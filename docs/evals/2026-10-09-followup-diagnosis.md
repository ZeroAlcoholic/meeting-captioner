### `services/online` 測試在本機是紅的

`pnpm -r test` 在 `services/online` 中斷，3 項失敗（146 passed／149）：

```
FAIL scripts/release-launcher.test.ts > 'Windows' release launcher > handles OPENAI_API_KEY ...
AssertionError: expected "'start.bat' 不是內部或外部命令…" to contain 'BUNDLE_STARTED'
```

根因（2026-10-09 修正，初判有誤）：測試以 `spawnSync('cmd.exe', ['/d','/c','start.bat'], { cwd: staging })` 啟動，倚賴 cmd 對裸指令名「先找目前目錄」的搜尋行為。本機環境帶有 `NoDefaultCurrentDirectoryInExePath=1`（Git Bash 等 MSYS 外殼會設定，用意是避免目前目錄被優先當成執行檔來源），該搜尋被停用，於是 cmd 找不到 `start.bat`。改傳腳本絕對路徑即通過。

初判曾歸因於暫存目錄前綴 `'meeting launch '` 結尾的空白；實測以絕對路徑啟動時，該前綴照樣通過，所以空白不是本缺陷的成因（它在其他執行期仍是隱患，見範圍外發現）。

這是測試本身的缺陷，不是發行腳本的缺陷。但後果有兩個：`pnpm -r test` 永遠在此中斷（web 測試根本跑不到），而且發行啟動腳本的「金鑰不外洩」回歸在本機從未真正執行過。

## 一、調查：有沒有「直出繁中」的方法

結論：**兩家都沒有可靠的直出繁中。用戶端轉換是正確選擇，但目前的轉換設定是錯的，而且它的載入方式正在拖慢啟動。**

### OpenAI `gpt-live-transcribe`

官方 realtime transcription 指南列出的 transcription 欄位是 `model`／`prompt`／`keywords`／`languages`／`delay`。`languages` 明確接受地區碼 `zh-cn`、`zh-tw`，並警告 `gpt-live-transcribe` 用複數 `languages`、不可同時送單數 `language`。

本專案 `services/online/src/routes/transcription.ts` **已經**送出 `languages: ['zh-tw','en']`、`delay: 'low'`，以及一段要求「中文使用繁體字」的 `prompt`。

**但 2026-10-08 真雲端實測的原始輸出仍是簡體**（`今天讨论会议逐字稿`、`请保留英文术语`、`确认`）。
直出繁中在 OpenAI 上**已經試過而且失敗**：`zh-tw` 與 prompt 是辨識提示，不是輸出字形保證。
（`delay: 'low'` 已在用，速度上這一項沒有剩餘空間。）
尚未用上的槓桿是 **`keywords`**。

### Gemini `gemini-3.5-transcribe-live`

官方 Live Transcribe 指南的 `inputAudioTranscription` 只有三個欄位：`language_codes`、`custom_vocabulary`（最多 1000 詞）、`mode`（`VERBATIM`／`SMART`）。
支援語言表中的華語只有 **`cmn-Hans-CN`（簡體普通話）**；繁體只有 `yue-Hant-HK`（粵語）。
**沒有任何輸出字形選項，而且 Live Transcription 不支援 system instructions。**

所以 Gemini 連名義上的繁中轉寫都不存在。
（`gemini-3.5-live-translate-preview` 支援 `zh-Hant`，但那是翻譯、會改寫原話，與純逐字稿的目標衝突。）
尚未用上的槓桿是 **`custom_vocabulary`**。

### 真正的問題一：轉換只做了字形，沒做用詞

`apps/web/src/providers/transcript-normalization.ts` 用 `Converter({ from: 'cn', to: 'tw' })`。
本機實測（`opencc-js` 1.4.2，非推測）：

| 上游輸出             | 目前 `to:'tw'`         | 改成 `to:'twp'`          |
| -------------------- | ---------------------- | ------------------------ |
| 视频会议软件         | 視頻會議**軟件**       | 視訊會議**軟體**         |
| 默认设置和鼠标       | **默認設置**和**鼠標** | **預設設定**和**滑鼠**   |
| 数据库信息           | **數據庫信息**         | **資料庫資訊**           |
| 这个项目             | 這個**項目**           | 這個**專案**             |
| 内存和硬盘           | **內存**和**硬盤**     | **記憶體**和**硬碟**     |
| 人工智能服务器打印机 | 人工智能伺服器打印機   | **人工智慧伺服器印表機** |

`'tw'` 只做字形轉換。上游送回來的是中國用詞，轉完仍是中國用詞，只是換成繁體字。
畫面上寫著「中文以台灣繁體顯示」，實際上**只有字形是台灣的，用詞不是**。

`twp` 的安全性也已實測：

- **對已經是台灣繁體的文字完全不動**（Gemini 有時直接吐繁體，例如「最後一句，明天下午三點再測試」原樣保留）。
- 英文、版本號、數字不受影響（`API latency p95 300 ms, deploy v2.3.1` 原樣）。
- 公司名正常（台积电→台積電、联发科→聯發科）。
- **`质量` 只會變 `質量`，不會變 `品質`**（物理的質量也是這個詞，OpenCC 刻意不猜）。→ 所以還需要一層專案術語表，不能只靠 `twp`。

### 真正的問題二：OpenCC 正在拖慢啟動

本機量測：

| 項目                                       | 數字       | 判讀                               |
| ------------------------------------------ | ---------- | ---------------------------------- |
| 熱路徑每行轉換成本（`tw` 與 `twp` 相同）   | **2.6 µs** | 對速度無影響，可以放心用 `twp`     |
| 建立 Converter（一次性，目前在模組載入時） | 40–60 ms   | 目前發生在開啟頁面時               |
| `opencc-js` 完整包 gzip                    | **497 KB** | —                                  |
| 目前主程式包 `index-*.js` gzip             | **624 KB** | **約八成是 OpenCC 字典**           |
| `opencc-js/cn2t` 子路徑 gzip               | 453 KB     | 只省 44 KB，真正的省法是別放進首屏 |

也就是說：**字典每次開啟頁面都要先下載解析完，使用者才看得到畫面**，而它其實只在第一段字幕出現前需要備妥。
第一段字幕最快也要在開始收音後約 1 秒才會出現，而連線建立、麥克風取得、Silero VAD 模型載入本來就要花掉這段時間——把字典改成在那段時間內平行載入，首屏可以直接少掉 497 KB，而且對字幕正確性零影響。

## 二、五項後續工作的診斷

### 1. 真人字幕品質驗收 — 缺的是「預測擷取」，不是評分器

- **已有**：`scripts/mixed-caption-eval.mjs` 是完整的離線評分器（CER／WER／critical terms／延遲 p95，門檻固定，拒絕可疑輸入，8 項自我測試）。`tests/fixtures/mixed-caption/cases.json` 有 24 個情境朗讀稿。
- **缺口 A（使用者端）**：沒有真人錄音與人工逐字稿。
- **缺口 B（工程缺口，目前沒人提）**：沒有任何東西能產生 `predictions.json`。評分器要 `firstTextMs`／`finalTextMs`，現有管線不輸出。`tests/e2e/pure-captions.spec.ts` 已能把 WAV 經原生 Chrome 餵進真實管線（`PURE_TEST_AUDIO`），差的是逐樣本迭代與時間戳記錄。
- 缺口 B 現在就能做完；做完之後錄音一到就能直接出分數，**而且它同時是調整斷句門檻的唯一量尺**。

### 2. 內外網主備切換 — 目前不具備可驗證的條件

- OpenAI 的雙金鑰與降級（`openai-keys.ts`）設計完整：mint 階段 401／403 自動換槽、呼叫階段由瀏覽器回報被拒槽位、30 分鐘 TTL 後回頭試主金鑰。
- **缺口 A**：**Gemini 只有單一 `GEMINI_API_KEY`**，沒有備用槽、沒有降級、沒有呼叫階段回報。
- **缺口 B**：**全專案沒有任何 HTTP(S) proxy 支援**。Node 22 的 `fetch` 預設不讀 `HTTPS_PROXY`。若內網必須走 proxy，token 鑄造會整個失敗，而錯誤訊息會長得像「服務拒絕」而不是「連不出去」。

### 3. 真雲端長會議與中斷 — 兩個結構性破口

- **破口 A：續期是「先斷後連」**。`TranscriptionSession.armRenewal()` 在 Gemini 8 分鐘（官方單 session 上限 10 分鐘）到期時 `stop()` → 排空（最長 5 秒）→ 重新鑄 token → 重開 WebSocket。期間 `audio.pause()` 已把來源斷開，**這段語音不送往任何地方，也沒有留存**。一小時會議在 Gemini 上就是 7 次必然缺口，每次約 1–6 秒。線上翻譯路徑早就做過零空窗的 make-before-break，純字幕路徑沒有。
- **破口 B：完全沒有原始音訊留存**。全專案找不到任何 PCM 環形緩衝。任何中斷期間的語音永久遺失，只能標成缺口。
- A 和 B 是同一個解：**只在記憶體、容量有界**的 PCM 環形緩衝（16 kHz 單聲道，60 秒約 1.9 MB），同時解掉續期缺口與短斷網。不落地、不可匯出、停止即清除，所以不需要先做錄音留存政策決定。

### 4. 完整逐字稿驗收與使用流程 — 基礎設施已到位

- 已有：SQLite 持久化、IndexedDB 獨立投遞佇列、原稿／校訂雙軌、修訂版號與樂觀鎖、缺口與未完成片段清單、TXT／SRT／JSON 匯出、保存狀態可視化、備份還原測試。
- **缺口 A**：SRT 時碼是擷取估計值且**允許重疊**（前輪刻意取捨）。重疊字幕在部分播放器行為不一致。
- **缺口 B**：沒有真人長稿做過一次完整四向對照，也沒做過備份還原演練。

### 5. 會議功能第二階段 — 契約層還沒有說話者的位置

- `packages/contracts` 整個找不到 `speaker` 欄位。`MeetingPayload` 只有逐字稿／翻譯／人工校訂／缺口四種。
- 語者指派也是一種人工修訂，必須和文字校訂一樣有版號、可還原、不覆寫原始辨識。摘要必須引用段落 ID 且走獨立通道，不得進入字幕熱路徑。
- 分段不穩定時做語者標註是白做，所以依賴前面的結果。

## 三、任務序（校準後，準備開工）

每個任務格式固定：**做什麼／速度影響／正確影響／驗收（必須可機械判定）／完成後得到什麼**。

通則（適用每一項）：

- **先取得失敗測試再改**。沒有先紅後綠的，不算完成。
- **證據配結論**：合成音訊只能支持「管線正確」，永遠不能支持「辨識品質可用」。
- **任何進入字幕熱路徑的改動**都要帶量測數字，不得只說「應該很快」。
- **每次雲端實驗**記錄：模型、session 設定、音訊 SHA-256、環境、去識別原始事件、分數、延遲、音訊時數、估算費用。
- **holdout 不得用於調參**；調過 prompt／keywords／斷句門檻／轉換設定後，必須用未動過的 holdout 重跑。
- 每項完成後更新 `docs/PROJECT_STATE.md` 與 `docs/TODO.md`。

- 速度／正確影響：無（測試基礎建設）。

**T1 — 中文轉成台灣用詞（`twp` ＋ 專案術語表）**

- 做什麼：`transcript-normalization.ts` 由 `to:'tw'` 改為 `to:'twp'`；在同一套「保護區段」機制內（現有已保護 URL 與 email）再加一層專案術語表，處理 `twp` 刻意不猜的詞（如 `質量`→`品質`、`訪問`→`存取`），術語表集中成一份可檢視的對照檔。

- 正確影響：這是一種改寫，但 `rawText` 已保留上游原文、原稿／校訂雙軌不變；實測對已是台灣繁體的文字不動、對英文與版本號不動。風險遠小於目前「宣稱台灣繁體卻顯示中國用詞」。
- 驗收：固定對照表測試先紅後綠（至少涵蓋 軟體／資訊／預設／設定／滑鼠／資料庫／專案／記憶體／硬碟／網路／連線／影片／互動／人工智慧／伺服器／印表機／品質）；**冪等測試**（已是台灣繁體的輸入必須原樣輸出）；URL／email／英文術語不被改動；匯出「原稿」仍是未轉換文字、「校訂版」是轉換後文字，兩者在同一份 JSON 內可區分；既有 665 項不退步。
- 完成後：**字幕與逐字稿的用詞真正是台灣的，而不只是繁體字形，而且原文沒有被銷毀。**

**T2 — 把 OpenCC 移出首屏**

- 做什麼：改用 `opencc-js/cn2t` 子路徑，並把 Converter 的建立改成在**開始收音時平行動態載入**（與 token 鑄造、麥克風取得、Silero VAD 模型載入同時進行），在 provider 進入 `running` 之前完成。
- 速度影響：**首屏 gzip 直接少約 497 KB**（主程式包 624 KB 中的八成）；載入搬到本來就要等 0.3–1 秒的視窗內，不增加第一段字幕的延遲。
- 正確影響：零。字典在第一個 partial 到達前就備妥；若載入失敗則視為 provider 啟動失敗，不會出現「先顯示簡體再換掉」的畫面。
- 驗收：建置後主程式包 gzip 明顯下降並記錄前後數字；載入失敗的注入測試證明不會以未轉換文字上字幕；第一段字幕延遲在既有受控上游測試中不退步。
- 完成後：**開啟頁面明顯變快，而且字幕該有的轉換一秒都沒少。**

**T3 — 預測擷取工具（`predictions.json` 產生器）**

- 做什麼：以現有原生 Chrome 管線逐樣本播放 WAV，記錄「首次非空文字呈現時刻」與「該樣本 final 到達時刻」，輸出符合 `mixed-caption-eval.mjs` 格式的 `predictions.json`。時間一律取自同一個單調時鐘；量不到的欄位必須省略，不可填 0。
- 速度／正確影響：無（量測工具，不進產品路徑）。
- 驗收：用現有合成 WAV 產出的 `predictions.json` 能被 `mixed-caption-eval.mjs` 接受並評分（exit 0 或 1，不得 exit 2）；同一批輸入連跑兩次，延遲差異逐次記錄而非平均掩蓋；跨句串流必須依實際 item 關聯對齊，工具要能拒絕「按事件到達順序盲配」。
- 完成後：**錄音一到就能一道指令出 CER／WER／關鍵詞／延遲報表；同時這是 T4 調斷句門檻的唯一量尺。**

**T4 — 斷句門檻參數化與量測（先量，不調值）**

- 做什麼：把 `TranscriptionSpeechGate` 的三個常數（800 ms 前置回看、700 ms 靜音尾、30 s 強制切段）參數化並可從設定注入；用 T3 的工具在固定語料上量出每組參數的首字延遲與 final 延遲分布。**本任務不選定新值**，只讓它變成可量、可調。
- 速度影響：final 延遲的七成由 700 ms 靜音尾造成，這是最大的一塊可調空間。
- 正確影響：調短會切碎句子，而 Gemini 是逐活動定稿，切碎會損害上下文與正確率。**所以不能憑感覺調**，必須等 T10 的真人資料。
- 驗收：參數化後既有測試不退步；至少三組參數在同一語料上的延遲分布有紀錄；30 秒強制切段的路徑有明確的回歸測試（連續不停說話時仍會產生 final，且標上續段關係）。
- 完成後：**「字幕慢」第一次變成一個可以用數字調整的旋鈕，而不是只能抱怨。**
- 2026-10-09 收尾補記：參數化本身引入一個缺陷，已修。`lookBehindMs` 小於一幀（掃描時一定會試的 `0`）時，前置回看的修剪迴圈會把剛到的那一幀也丟掉，`this.preRoll[0]!.start` 隨即在音訊幀回呼裡丟 TypeError——真實會議中等於整條音訊管線停擺、字幕不再更新。修剪改為永遠保留剛到的那一幀，並補上回歸測試（先紅後綠確認）。預設值的既有斷言全數原封通過。

**T5 — 送出術語提示（OpenAI `keywords`、Gemini `custom_vocabulary`）**

- 做什麼：把會議術語清單帶進兩家 session 設定；路由層驗證格式與上限（OpenAI 每詞一行、不得含 `<` `>` CR LF；Gemini 上限 1000 詞），超量必須明確報錯而非靜默丟棄。術語表與 T1 的台灣用詞對照表共用同一份來源。
- 速度影響：無（在 session 建立時送出，不在熱路徑）。
- 正確影響：這是提升 `critical terms recall ≥ 95%` 的官方手段，目前完全沒用。
- 驗收：路由層測試涵蓋格式驗證、截斷與拒絕；受控上游測試確認欄位確實送出；**此任務不宣稱辨識有改善**（那要等 T10）。
- 完成後：**關鍵詞保留率這條門檻第一次有可調的工程手段，而且和台灣用詞表是同一份來源，不會兩邊打架。**
- 2026-10-09 驗收補記：本項的路由斷言是先改路由才補測試，不符先紅後綠。改以變異測試補證——分別刪掉 `transcription.ts` 的 `keywords` 與 `gemini-transcription.ts` 的 `customVocabulary` 後重跑，`services/online` 由 157 綠變成 2 紅（兩條路由各一），還原後回到 157 綠，確認斷言真的在守這兩個欄位。

### 第二梯：讓長會議不再必然掉字

**T6 — 記憶體 PCM 環形緩衝**

- 做什麼：16 kHz 單聲道、上限 60 秒（約 1.9 MB）的環形緩衝。**不落地、不可匯出、停止即清除**，不改動任何既有保留政策。
- 速度影響：寫入是定長複製，不配置記憶體，不進 VAD 推論路徑。
- 正確影響：無（純留存，尚未改變送出行為）。
- 驗收：單元測試證明容量上限、覆寫順序、停止後清空；長測中記憶體上限不被突破（沿用 `pure-soak` 既有 heap 斷言）。
- 完成後：**系統第一次有能力補回中斷期間的語音，而不是只能標缺口。**

**T7 — 續期改成 make-before-break ＋ 中斷重播**

- 做什麼：新連線 `setupComplete` 之後才切換舊連線；切換期間的音訊由 T6 緩衝補送；邊界去重。短斷網重連時同樣重播緩衝區。
- 速度影響：切換期間字幕不再中斷，使用者看不到停頓。
- 正確影響：這是目前長會議唯一的結構性掉字來源，修掉等於直接提高正確率。
- 驗收（**精準性關鍵**）：用**連續計數語料**（連續朗讀編號的音訊）跨越一次續期與一次人為斷線，檢查輸出數列**無缺漏、無重複**。只看 UI 沒有缺口標記不算通過——那只證明沒標，不證明沒掉。
- 完成後：**一小時 Gemini 會議從「7 次必然缺口」變成「0 次」，而且是用可數的語料證明的。**

### 第三梯：網路韌性（純工程，可自行驗證）

**T8 — Gemini 備用金鑰槽與降級，與 OpenAI 對齊**

- 做什麼：加 `GEMINI_API_KEY_BACKUP`；mint 階段 401／403 換槽、呼叫階段由瀏覽器回報被拒槽位、TTL 後回頭試主金鑰。單金鑰部署行為必須完全不變。
- 驗收：以假上游注入 401／403，驗證換槽、降級記錄與 TTL 回復；單金鑰設定下行為與現在逐項相同。
- 完成後：**兩家後端的失效切換能力對等，不再是「OpenAI 有、Gemini 沒有」。**

**T9 — 伺服器端 proxy 支援**

- 做什麼：`undici` ProxyAgent，讀 `HTTPS_PROXY`／`NO_PROXY`；啟動輸出明確顯示是否走 proxy、走哪一個（不印憑證）。
- 驗收（**有效性關鍵**）：指向本機假 proxy 時，**假 proxy 必須實際收到 CONNECT 並計數**，不能只看「請求成功了」（那可能是直連）；`NO_PROXY` 命中時必須走直連，且同樣以計數驗證。
- 完成後：**第一次可以在公司網路上做實驗，而且失敗訊息能分辨是權限問題還是網路問題。**

### 第四梯：需要使用者提供外部條件

**T10 — 真人混語品質與延遲驗收，並據此定下斷句門檻**（前置：T1、T3、T4、T5；使用者提供可外送的錄音與人工逐字稿）

- 做什麼：依 `mixed-caption-eval-usage.md` 建 manifest，分 calibration／holdout（**以說話者與錄音 session 分組切分**，不得把同一段的衍生片段分散兩邊），兩家各自評測；用 calibration 集決定 T4 的斷句門檻值，再用未動過的 holdout 驗證。
- 驗收：逐場景 CER ≤ 10%、WER ≤ 15%、critical terms recall ≥ 95%；整體首字 p95 ≤ 2000 ms、final p95 ≤ 3000 ms；**逐例列出否定、金額、日期、版本、責任歸屬的錯誤**，不被平均值掩蓋；分開報「上游原文 CER」與「轉換後 CER」，把上游錯誤與用詞轉換錯誤分離；斷句門檻的選值必須附上延遲與正確率的取捨數據，不得只說「調短比較快」。
- 完成後：**第一次知道這套系統在真實混語會議上能不能用、兩家誰比較適合、錯在哪一層，而且速度是依資料調到位的。**

**T11 — 內外網主備切換實測**（前置：T8、T9；使用者提供授權網路環境）

- 驗收：主金鑰被拒 → 切備用 → 回內網復原，三段都有原始證據（去識別的狀態碼與時間序）；**不得以強制選槽的方式宣稱自動切換成功**；同時記錄是否存在獨立內網 proxy。
- 完成後：**在公司網路上開會時，金鑰被擋不再是當場停擺。**

**T12 — 真雲端長會議與中斷實測**（前置：T6、T7）

- 驗收：60 分鐘以上真帳號長測；記憶體有界（沿用既有 heap 斷言）；缺口清單與實際中斷逐一吻合；續期跨越處以計數語料確認無缺漏；累計音訊時數與費用逐次記錄。
- 完成後：**可以把這套系統帶進真實的一小時會議，而且知道它在斷線時會失去什麼、不會失去什麼。**

**T13 — 完整逐字稿四向對照與備份還原演練**（前置：T10 的素材）

- 做什麼：真人長稿的原稿／校訂／SRT／JSON 四向對照；備份還原演練；決定 SRT 重疊時碼的處理（維持重疊並在匯出說明，或提供「不重疊」選項）。
- 驗收：四種輸出內容一致；還原後逐段相同（含修訂版號）；缺口由人工核對確認；SRT 重疊行為有書面結論。
- 完成後：**逐字稿可以交付給沒有參與會議的人使用，而不只是「有存下來」。**

### 第五梯：會議功能第二階段

**T14 — 契約加語者欄位與人工語者標註**（前置：T10 的分段穩定度結論）

- 驗收：語者指派有版號、可還原、不覆寫原始辨識；既有測試不退步；匯出格式向下相容。
- 完成後：**逐字稿可以回答「這句是誰說的」。**

**T15 — 摘要、決議、責任人、待辦**（前置：T14）

- 驗收：每則引用段落 ID；摘要失敗不影響字幕、翻譯、收音與切換；摘要只吃 final 片段，不吃 partial。
- 完成後：**會後十分鐘內拿得到可追溯的會議結論，每一條都能點回原話。**

### 不建議現在做

- **落地錄音留存**：需要使用者先決定保留期間與範圍；T6 的記憶體緩衝已解掉當前的實際痛點。等 T12 看完真實斷線損失再決定。
- **離線純字幕**：仍保留在藍圖，本輪不動。
- **bundle 大小警告**：T2 會順帶大幅改善，不另外開重構。

## 四、全部完成後能達到什麼

1. **字幕是台灣的**：用詞與字形都是台灣繁體，術語表與雲端提示同一份來源，原始辨識完整保留可回溯。
2. **快**：開啟頁面少載近 500 KB；final 延遲的最大來源（自家斷句門檻）變成可量可調，並依真人資料定值。
3. **準**：兩家後端在真人混語會議上的 CER／WER／關鍵詞保留率都有數字，錯誤能歸因到上游或用詞轉換，holdout 沒有被污染。
4. **長會議不掉字**：續期與短斷網不再產生必然缺口，用可數語料證明；真的失去的部分會被誠實標成缺口。
5. **網路環境不再是單點**：兩家後端都有備用金鑰與降級，內網 proxy 有支援且失敗訊息可分辨。
6. **逐字稿可以交付**：原稿／校訂／SRT／JSON 一致，備份可還原，缺口經人工核對。
7. **會議產出可追溯**：知道誰說了什麼，摘要與待辦每一條都能點回原話，而且全部不影響字幕熱路徑。
