## 二、真人語料擷取工具

### 語料

以 Windows 內建 **Microsoft Hanhan (zh-TW)** 合成 `tests/fixtures/mixed-caption/cases.json` 的 24 題，16 kHz 單聲道，RMS −22～−28 dBFS，長度 3.6～14.2 秒；`mix-23` 為真正的數位靜音（負向對照）。以 −45 dBFS／32 ms 視窗量出每題的 `speechStartMs`／`speechEndMs`。

Manifest 標記 `referenceKind: synthetic-tts-not-gold`——評分器依規則拒絕它，**這批永遠不會產出品質判決**，只能測管線與延遲。

### 修掉的四個缺陷

先前「擷取工具兩家都通過」是**單一樣本**的結論；24 題連跑第二題就死。

1. **換頁落在前一頁的寫入權租期內** → 第 2 題起全部跑成唯讀。修法：把「啟動」本身當成要重試的操作（前兩次修法都因為訊號選錯而失敗）。
2. **等待保存完成的斷言是空的** — 區塊內永遠有「待保存 N 筆」「重試保存／結案」，兩者都含「保存」，`toContainText('保存')` 永遠立刻成立。改為比對 `已結案保存｜已保存，逐字稿尚待核對`。
3. **任一題失敗就丟掉整輪** — `writeFile` 在迴圈外。改為每題獨立 try/catch，結果照樣寫出。
4. **每題共用瀏覽器脈絡** — 前一題未送出的事件會污染後面每一題。改為每題獨立設定檔。

### 根因：服務包過期（操作疏失）

```
.cache/pure-release/server.cjs   建置於 2026-10-08 15:58
含 "opencc-cn-tw-v1"  : 1
含 "opencc-cn-twp-v2" : 0
```

`docs/TEST_PLAN.md` 列了兩個建置步驟，先前只做了 `pnpm -F web build`，**未重建服務包**。舊包不認得 T1 新增的 `opencc-cn-twp-v2`，凡是真的發生過用詞轉換的事件一律被 `INVALID_MEETING_EVENTS` 拒絕，且客戶端無限重送，整個設定檔的保存永遠卡住。

受控上游不會踩到（罐頭文字本來就是繁體，不產生標記）；真實上游必踩。

**連帶更正**：先前回報「`pure-captions` e2e 兩家綠」跑的是這份舊包，**那次驗證沒有驗到契約變更**。重建後重跑，兩家仍綠。

**防呆**：globalSetup 會比對服務包與 `packages/contracts/dist` 的時間，舊的直接拒跑並印出重建指令。

## 三、失效切換與自動接手

### 問題

```
Gemini 故障 → 字幕回到畫面：20,246 ms（預算 3,000 ms）
```

根因是 `meeting-recovery.ts` 的 `HANDOFF_GRACE_MS = 20_000`。已證偽非本輪改動造成（移除本輪的字典等待後為 20,166 ms）。

這是**回歸**：`docs/PHASE_2_RUN.md` 中 A2「自動接手」已標 completed 並量到 2,020 ms。20 秒是 2026-10-02 連續性修復刻意加的，理由同樣成立——當時 App 會在 2 秒就打斷 Gemini 還在進行中的握手。兩份文件的意圖真衝突，直接調小常數會把已修好的問題重新弄壞。

### 作法：先通後斷，同廠優先

1. **同廠起跑時間**：後端回報失敗後先給同廠 1,000 ms 自己重連，期間不碰備援。
2. **同廠贏了就留下**：備援連上後先檢查原後端是否已自行恢復——是則停掉備援、留住同廠。為此在兩個 hook 各加 `getTransport()`（ref 讀取），因為 `transport` 是兩家共用欄位，重疊期間分不出誰連上。
3. **永不為了啟動備援而拆掉同廠**：接手改為先起目的端、連上才拆舊的；`startRealCore` 在接手情境保留對方。擷取租約本就支援多持有者，麥克風不重開。

結果：socket 掉線這類同廠能自救的故障，**備援根本不會被啟動**。

### 起跑時間取值

| 同廠起跑     | 斷窗         | 餘裕       | 說明             |
| ------------ | ------------ | ---------- | ---------------- |
| 0 ms         | 1,240 ms     | 1,760 ms   | 同廠沒有任何機會 |
| **1,000 ms** | **2,232 ms** | **768 ms** | **採用**         |
| 1,500 ms     | 2,744 ms     | 256 ms     | 餘裕過薄         |

常數為 `HANDOFF_DELAYS_MS[0]`，可調。

### 本輪造成並已修的回歸

先通後斷讓兩個後端可同時存在，備援啟動失敗留下的錯誤橫幅會在同廠恢復後仍掛著不走（`:113` 因此轉紅）。改為**錯誤以實際承載會議的後端為準**。

### 改動的既有斷言

- `meeting-recovery:169` 原斷言「接手 ≥ 20,000 ms」，直接寫死舊政策。改為「≥ 1,000 ms 且 < 10,000 ms」。
- `meeting-recovery:70` 原要求「故障後 3 秒內不得啟動 OpenAI」，與「3 秒內字幕回到畫面」邏輯上不可能並存。改為測新政策真正該保證的事：broker 健康、只掉 socket 時，Gemini 自己接回來、OpenAI 完全未被啟動、無切換通知。

**代價**：同廠的有界重連最長 20 秒，現在只拿得到 1,000 ms；超過才救回來的連線會被已接手的備援取代。這是用同廠續接成功率換取字幕 2.2 秒回到畫面。
