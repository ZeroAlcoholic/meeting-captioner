# 台灣繁中與原文混用字幕：診斷與會議功能藍圖

日期：2026-10-08。狀態：**規劃提案；未實作、未重啟服務、未進行付費音訊驗證。**

本文件回應「先純字幕，再完善語者、點列摘要及議題脈絡」。既有工作區包含多項未提交變更；本輪僅新增規劃與更新文件索引，不改產品程式。

**最新目標補充：** 使用者要求「精準字幕與完美會議逐字稿留存」，並允許施工期間關閉服務。第一個正式交付因此必須包含 A 純字幕＋B 完整地端保存，兩者是實作順序而非可任意省略的交付範圍。施工可經 managed 入口停止本工作區服務，不授權終止其他服務；本輪仍先完成規劃。

## 1. 建議決策

第一步交付「純字幕／保留原文」工作模式：國語以台灣繁體中文呈現，穿插的英文、縮寫、產品名與原文術語保留原樣；沒有翻譯目標、模型回話或語音輸出。不是新增 `zh-TW→zh-TW` 翻譯方向。

採用獨立 transcription provider，重用已驗證的音源、擷取所有權、恢復協調及 normalized event 介面。字幕立即顯示；保存、語者補註與摘要是後續消費者。第一階段先線上垂直切片，Offline 保持真實能力與可用性標示，不假裝線上功能等於離線支援。

| 選項                               | 優點                                 | 實際問題                                       | 建議           |
| ---------------------------------- | ------------------------------------ | ---------------------------------------------- | -------------- |
| 翻譯服務增加繁中→繁中              | 改動表面較少                         | 仍走翻譯、語言抑制及雙字幕假設；英文可能被翻譯 | 不採用         |
| 專用即時轉寫＋原文顯示             | 語意與需求一致；字幕與摘要可分開驗收 | 需新 token/session、事件轉接與目的感知恢復     | 優先           |
| 一個多模態模型同時字幕、辨人、摘要 | 入口看似集中                         | 難隔離延遲、錯誤與成本；不能保證忠實逐字稿     | 不作主字幕路徑 |

「繁中」是中文顯示政策，不代表輸入只能中文。第一版驗收語料以國語＋英文為主；日文、台語或其他原文如為實際需求，必須加入語料及模型能力驗證，不能由「保留原文」推論成支援所有語言。

## 3. 第一階段產品契約

### 3.1 字幕保真

- 輸入：「這個 sprint 的 scope 先 freeze，API latency 目標是 p95 300 ms。」輸出保留 sprint、scope、freeze、API latency、p95、300 ms。
- 輸入：「不是 approve，是 pending review。」不可改成已批准；保留更正、否定與原文。
- 日期、金額、版本號、email、URL、縮寫、公司及人名納入 gold corpus；不能以中文 CER 一個平均值掩蓋術語錯誤。
- 允許繁體字形與合理標點，不在字幕路徑做 LLM 潤稿、摘要、推理補字或翻譯。模型原始文字與顯示文字可追溯；無法從文字保證 ASR 正確。
- 詞彙表只給辨識提示，不強迫補入未說出的術語；保存詞彙表版本供品質比較。第一版用小型測試詞表，不另建詞庫管理產品。
- 不做文字相同即去重；連續兩次「對，對」可能是有效發言。依 provider item／事件生命週期去重。

### 3.2 工作目的、部署模式與狀態分離

`purpose = transcription | translation` 與既有 `Mode = online_full | hybrid_privacy | full_offline` 不同。純字幕預設語言提示 zh-tw＋en、保留原文；translation 的兩個 LangPair 不變。

既有使用者遷移後保留原翻譯設定；新選項清楚顯示「純字幕（繁中＋原文）」。第一版會議開始後鎖定目的，停止再改，避免同一次會議意外混用 session／計费／歷史語意。每次 Retry 保留會議歷史；新會議與連線 generation 不同。

純字幕只產生 TranscriptEvent，partial 可修訂、final 可保存。沒有上游依據時不產生 confidence、speakerId、逐字時間或自動語言識別標籤。翻譯計時／成本不能冒用純字幕計價；價格未驗證時顯示未知，不能顯示免費或 0。

### 3.3 第一版完成邊界

A 階段完成表示：可開始、看到混語字幕、停止、同目的恢復及匯出目前保留文字；不代表已可永久保存整場會議。必須標示尚未保存／保存狀態及匯出範圍，避免把有界歷史當完整紀錄。

A＋B 才能宣稱具備可回復的整場文字紀錄；D/E 摘要引用依賴 B，不能從被淘汰的 UI cache 產出「完整會議摘要」。文字保存不等於錄音保存，也不能補回未取得的音訊。

依最新要求，A 單獨通過只算工程里程碑，不可當作第一版已完成。B 的自動保存、停止結案核對、重開恢復、完整匯出、修訂留痕及已知缺口清單都是首版必要條件。

「完美」轉為可驗證的工程目標：已確認保存的事件重啟後 100% 可取回；正常結案沒有未處理的待存事件；匯出與同一 revision 的資料庫一致；所有已知中斷／未完成回合有紀錄。語音辨識則用語料與人工校對評測，不能保證未被偵測的辨識錯誤為零。逐字稿保留口語、否定、自我更正與有效重複；可讀版或摘要另存，不能覆寫原稿。

若要事後逐句核對聲音或修正未辨出的字，必須有可使用的原始錄音；僅保存模型 rawText 不能提供該證據。第一版提供人工文字校訂與原稿／修訂版本；是否同時保存可回放音訊，需在 A0 明確決定保留範圍、期限與授權，不由「逐字稿留存」默認啟用錄音。沒有錄音時明示其可校對範圍。

## 4. 技術方案與模型選擇門檻

2026-10-08 查核的官方即時轉寫指南將 `gpt-live-transcribe` 列為建議模型：transcription session、zh-tw/en 語言提示、24 kHz PCM；該模型需客戶端斷句提交，不使用 server_vad/semantic_vad。完成事件可能亂序；模型不提供語者、逐字時間或信心分數。這些限制要求新 adapter，不能複製翻譯協定。[官方即時轉寫指南](https://developers.openai.com/api/docs/guides/realtime-transcription)

因此將它列為**首選評測候選**，並非已證明優於現有模型，也不是帳號已可用。執行 A0 時確認當日 API 契約、帳號權限、SDK 相容、價格與最小測試預算，才凍結模型／transport。若不通過，選另一個經實測的 transcription 模型並記錄差異；不能默默降級成翻譯。

建議先驗證瀏覽器 WebRTC＋ephemeral token 與 client commit 的完整路徑，沿用擷取權限及恢復架構。若必須用 WebSocket，先驗證瀏覽器驗證方式及音訊格式；需要 relay 時掛在現有 Fastify，同一來源／埠，不另開服務。只落地通過 A0 的一種 transport，避免同時養兩套未驗證協定。

音訊處理必須維持連續時鐘與 resampler 狀態。復用可用 VAD 元件前先查現有依賴；不能僅用固定秒數切片或簡單音量門檻冒充可靠 VAD。以 speech-end 觸發 commit；連續講話的有界分段要保留前後段關係，處理尾音、短停頓、靜音、重疊發言與 stop flush。item_id 對應送出回合的順序及音訊時間，不能用 final 到達順序排字幕；精確 ack 欄位以 A0 實測契約為準。

建議資料流：

```text
音源 → 擷取所有權／連續音訊時鐘 → 專用轉寫 provider
                                   ↓ normalized TranscriptEvent
                         字幕 store → 單欄字幕（立即）
                                   ↓ finalized / revisions（非阻塞）
                      地端 durable log → 語者補註 → 摘要／議題
```

保存、語者及摘要失敗只顯示各自狀態，不停止字幕。各背景 queue 有大小與逾時上限；儲存失敗不能回報已保存，超出未保存緩衝必須明示缺口，不能以「不阻塞」合理化靜默丟資料。

### B：保存的具體界線

沿用 [既有 continuity spec](2026-10-02-meeting-continuity-design.md) 的單 writer、transaction commit 後 ACK、冪等重送與 tab lease。資料位於 `%LOCALAPPDATA%\MeetingAudio\` 或明確設定的資料目錄；不放 managed build cache。worker 不增加 HTTP 埠。

新增 meeting metadata 記錄 purpose、語言政策、模型與字形轉換版本；TranscriptRevision 保存原始／顯示／人工更正的來源與版號。會議、provider session、音源 track、speaker identity 分開；斷線重連不另開會議，換會議不可復用舊 identity。

刪除／匯出／保留期限需使用者可理解；已 ACK 的內容和仍在 outbox 的內容分別顯示。全稿匯出從 durable history 讀取。要驗证多分頁、重啟、磁碟滿、重複提交、revision 亂序及新會議不覆寫舊會議。

### C：語者不是麥克風名稱

mic／system 是來源，不是人；一支麥克風可多人，system track 也可含全部遠端參與者。先顯示「麥克風／遠端音訊」，不能稱為「語者 A/B」並暗示已分人。

後續語者標籤用會議內 speakerId、可人工命名／合併／拆分、每段 association 版本及 unknown/overlap 狀態。名字只能來自可靠參與者對應或人工確認，不能依聲音猜名字。語者更正影響摘要 attribution，但不修改原始轉寫。

可評測檔案式 `gpt-4o-transcribe-diarize` 作延後補註候選：diarized_json 帶語者及時間，超過 30 秒需 chunking_strategy；已知語者參考有數量及片長限制。這是另一條音訊處理路徑，不能等同純字幕模型即時自帶語者。[官方檔案轉寫指南](https://developers.openai.com/api/docs/guides/speech-to-text)

錄音緩衝／保存／二次雲端上傳不是本次純字幕的默認前提；需另定期限、成本與授權。未允許時仍可用手動標記，清楚表明自動辨識不可用。以 DER、未知／重疊比例、跨批次誤合併及責任歸屬錯誤評測，不只看文字正確率。

### D/E：摘要與脈絡的可追溯資料

每筆摘要項目至少包含：`meetingId`、`kind`（fact/proposal/decision/action/open_question）、文字、引用的 `segmentId + revision`、議題關聯與摘要自身 revision；owner／due 可缺省，不猜測。若引用內容被修正，標示 stale 並只重算受影響項目，保留變更紀錄。

draft 是尚在整理；refined 已經整合；stable 是當下可引用版本，不代表後續永不可更正。只有 final 轉寫進摘要，partial 的來回修字不能反覆製造待辦。

議題脈絡要保存「問題 → 方案／理由 → 決議或未決 → 行動 → 後續更正」；同議題可離開再返回。長會議用分窗處理＋有引用的事實／決策索引＋回讀原文，不僅反覆摘要既有摘要，以免原始例外與否定被逐層抹掉。補充議程／附件須另標來源，不能偽裝成與會者發言。

摘要工作用非阻塞、有界佇列；斷網／配額／模型失敗顯示「摘要暫停」，字幕照常；恢復後依已保存 cursor 追上。摘要 UI 預設收合，狀態及最後涵蓋到的時間可見；點列可跳回原句、責任人未知清楚列出。

既有政策要求 LOCAL 能完成的 LOG/TEXT 處理由本機完成。保存、索引、切窗、引用、匯出優先本機；語意模型另評測本機可用模型的硬體／品質。若要雲端摘要，需明確界定文字外送與成本，不能把本次功能規劃視為已允許把整份逐字稿再送雲端。無合格本機模型且未授權雲端時，這是 D 的實作決策門檻，不用規則式假摘要充作完成。

## 6. UI 最小調整

- 啟動：工作目的「純字幕／即時翻譯」；純字幕下顯示「中文以繁體顯示，英文與原文保留」，只列通過能力檢查的服務。
- 字幕：單主欄、大字、partial 到 final 穩定替換；不出現翻譯中、目標語言空白欄或人工複製出的雙字幕。
- 狀態：收音／連線／字幕／保存分別回報；無聲、辨識中、重連、已停止可區分；未知支援不裝成正常。
- 後續工作區：字幕主區＋可收合「重點／決議與待辦／議題」側欄；語者更名在逐字稿上操作。第一階段不先塞入空白摘要面板。
- 匯出：原文字幕為預設；B 後整場逐字稿；D/E 後會議紀錄含引用。ASR 推估時碼與人工修訂有 provenance。

## 7. 風險、驗收證據與執行門檻

最高風險依序：混語被翻譯或中文化、模型／協定在帳號不可用、回合提交漏尾音／亂序、恢復誤切服務、UI 歷史被當全文、語者誤認導致責任歸屬、摘要把提案寫成決議。

先建立小而有代表性的 gold corpus：至少 24 段，國語、中英句內切換、英文完整句、術語／數字／否定、近講／遠場／多人／靜音均覆蓋；另保留未參與提示詞調整的測試集。由可使用的真實錄音或明確同意的測試錄音建立，不能以合成單句涵蓋所有情境。

A0 先測 baseline，再把品質門檻寫成固定驗收值；初始目標建議中文 CER ≤10%、英文 WER ≤15%、領域關鍵詞 ≥95%，發話開始到第一可讀片段 p95 ≤2 秒、語音結束到 final p95 ≤3 秒。這些是待評測目標，非已測能力或承諾；資料量、場景及失敗例必須一起報告。數字／否定／決議等關鍵錯誤逐例列出，即使平均過關仍需審查是否可接受。不能測完才悄悄放寬門檻。

結構正確性是硬門檻：不送翻譯請求、不輸出模型語音、不假語者、不洩漏 keys；舊 generation 不改新狀態；Stop 後不重連；所有已取得 final 正確順序且不重複。Chrome 的原生音訊／transport 測試與付費真服務品質測試分開記錄。

長測分開：60 分鐘本機原生音訊驗證檢查記憶體、回合、UI、恢復；真雲端先做最小已核准預算的測試，再決定更長驗證。mock、Demo 或舊翻譯測試通過都不能取代新 transcription 的真實驗收。不得為測試另起一套不明服務；日常依 `pnpm service:status/start`，用 status URL。

實作前仍須解決的具體門檻：A0 帳號及協定、實際混語語料與品質基準；付費測試金額上限；C 的音訊使用政策；D 的本機硬體及文字外送選擇。它們不妨礙本次規劃完成，但不能在實作時默默當成已確認。
