# 工作區瘦身技巧與重點

> 來源：2026-11-16～19 的工作區空間診斷與清理（`docs/disk_bloat_audit_2026-11-16.md`、`docs/disk_cleanup_list_2026-11-19.md`）。
> 成果：5,100 MB、288,870 檔，降到 1,547 MB、42,903 檔。被引用的證據、交付包與 41 個保護來源都沒有受損。

---

## 1. 量測：先確定數字是真的

| 技巧                  | 重點                                                                                 | 不這樣做的後果                                                 |
| --------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| 用長路徑前綴遍歷      | Windows 用 `\\?\D:\…` 開頭的根路徑走全樹，並記錄讀取錯誤數，錯誤數必須是 0           | 超過 260 字元的路徑會被靜默跳過；本案漏了 240 檔               |
| 依內容判定重複        | 先依大小分組，大小相同的再算 SHA256；浪費＝Σ(份數−1)×大小                            | 依檔名判斷會漏算或誤判                                         |
| 用 `os.stat` 查硬連結 | 看 `st_nlink`、`(st_dev, st_ino)`；Windows 的 `DirEntry.stat()` 這兩欄恆為 0，不可用 | 會把已共用的資料當成重複                                       |
| 依 inode 合併加總     | 有硬連結時，同一個 inode 只算一次                                                    | 硬連結去重的效果量不出來                                       |
| 分開看檔案數和空間    | 依大小分層統計（例如以 10 KB 為界）                                                  | 被大量小假檔誤導；本案 1.3 萬份 `.m4a` 中只有 212 份是真實錄音 |
| 原始碼不含快取        | `__pycache__`、`.pytest_cache` 單獨列                                                | 原始碼大小被高估（本案高估 77%）                               |
| 看磁碟實際佔用        | 叢集大小用 `Win32_Volume.BlockSize` 查；小檔有尾端浪費                               | 低估刪除大量小檔可收回的空間                                   |

**Bash 環境注意**：本機 Bash 工具會把 heredoc 和 `-c` 參數裡的反斜線減半。Python 腳本裡一律用 `chr(92)` 組出反斜線，並以 `-I -X utf8` 執行。

## 2. 判定：「可以刪」要一層一層證明

1. **查引用**：在所有版控檔和未追蹤檔中，搜尋 `temp/<名稱>`、`output/<名稱>` 這種路徑形式。
   - 正反斜線、絕對路徑（如 `C:\Develop\HR\temp\…`）都要算，不分大小寫。
   - 只搜裸名稱會誤判：名稱也會出現在測試和報告裡。
2. **查內容**：沒被引用，不等於沒價值。臨時腳本可能是證據的產生程式，歷史結果可能只存這一份。
3. **查副本**：刪除或去重前，逐檔確認別處有位元組相同的正本。
4. **查依賴**：確認有沒有程式依路徑找檔案。
   - 例：「核聽原音」要在案件資料夾內找到 SHA256 相符的錄音（`workflow/candidate_store.py:373-392`）。
   - 例：有沒有程式會就地改寫檔案（`scripts/unpack_newdata.py:230`）。
5. **查保護清單**：受保護的來源（`output/fay_calibration_20261029/source_hashes.json`）不可落在清理範圍內。

## 3. 分級：依「能否重建」和「是否唯一」分類

| 級   | 判準                               | 處置             | 本案                    |
| ---- | ---------------------------------- | ---------------- | ----------------------- |
| A    | 能重新產生：測試暫存、快取、空目錄 | 直接刪除         | 548 項、1,405 MB        |
| B    | 沒被引用，但可能只存一份           | 逐項由使用者決定 | 63 項、166 MB（未刪）   |
| C    | 內容和正本相同，但路徑要保留       | 換成硬連結       | 186 份錄音、2,148 MB    |
| 保留 | 被引用、受保護、可能用於重現證據   | 不動             | 引用 42 項、腳本 345 支 |

**判斷原則**：如果刪掉某項省下的空間很小，卻可能失去重現能力，就保留它。

## 4. 執行：先列後做，前後都驗

1. **產出清單**：人看的 `.md` 加上機器讀的 `.json`。執行時以 JSON 為準。
2. **取得同意**：逐級取得同意，不可擴大範圍。
3. **執行前比對**：每一項的檔案數和大小都必須和清單相同。有任何一項不符，就停下回報，不刪除。
4. **執行前讀數**：保護來源雜湊、依 inode 合併的佔用、檔案數。
5. **刪除單獨一步**：只刪清單上的路徑；確認每個路徑都在專案範圍內，不跟隨連結或交接點（junction）。
6. **硬連結替換**（每一份依序做）：
   - 在同一目錄建立暫時名稱的硬連結。
   - 驗證它的 SHA256。
   - 用 `os.replace` 原子替換原檔。
   - 再驗一次 SHA256，並確認連結數大於 1、inode 和目標相同。
   - 任何一步失敗，就保留原檔。
7. **執行後讀數**：重算同一組讀數，並確認保留項目的檔案數和大小沒變，也沒有殘留的暫存連結。
8. **寫回紀錄**：在報告裡附上前後讀數，並引用使用者授權的原話。

---

## 5. 硬連結：用之前要知道的限制

- 連結和正本必須在同一個磁碟區。
- 修改其中任何一份，會同時改到全部。有程式會就地改寫的目錄，不可以用硬連結。
- 複製或壓縮含連結的資料夾，會變回完整副本。
- 刪除正本不會釋放空間，因為其他連結仍指向同一份資料。
- 因此要另外留一份**實體備份**。本案為 `data/_backup/candidates_audio_20261119.zip`，內附 `manifest.json`，記錄雜湊和所有連結路徑。
- `.m4a` 等已壓縮的格式，再壓縮幾乎不會變小。備份的目的是保留獨立的一份，不是省空間。

## 6. 治本：防止再膨脹

| 根因                                           | 對策                                                                                               |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 每輪重測都複製整個案件資料夾（含錄音）         | 只記錄原音路徑和 SHA256；需要隔離資料夾時，改用硬連結                                              |
| 測試暫存寫進專案、沒有清理（`HANDOFF.md:319`） | basetemp 改放 `.tmp/`，跑完就刪，或定期清理超過 7 天的；`.gitignore` 補上 `.tmp/`                  |
| 合成測試音過大（單檔 13.73 MB）                | 改用 KB 級的合成音                                                                                 |
| 在工作區產生專案快照                           | 程式靠 git 標籤回滾；資料只記錄雜湊清單                                                            |
| 膨脹沒有人發現                                 | 加一道容量閘：測試或驗收結束時回報 `temp/`、`output/` 的大小和檔案數，超過門檻就報錯，並附雙側測試 |

## 7. 常見誤判（本案實際犯過）

| 誤判                       | 正確做法                                             |
| -------------------------- | ---------------------------------------------------- |
| 「全量盤點」卻靜默漏檔     | 記錄讀取錯誤數；用長路徑前綴                         |
| 把快取算進原始碼           | 快取單獨列                                           |
| 依檔案數判斷主因           | 依空間判斷；本案主因是驗收重測複製錄音，不是單元測試 |
| 「沒被引用＝零風險」       | 再看內容是否唯一、能否重建                           |
| 依資料夾名稱猜正式資料來源 | 以設定檔為準（`settings.toml:5`）                    |
| 建議把暫存寫到專案外       | 依寫檔邊界規則，暫存只放專案內 `.tmp/`               |

**總原則**：空間清理的風險不在刪除這個動作，而在判斷錯誤時沒有被攔下來。每一項主張都要有可以重跑的探針，最後再做一輪獨立審查。
